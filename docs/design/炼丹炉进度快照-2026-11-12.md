## 1. 产品主线与当前定位

目标仍是**面向个人、可跨领域迁移的灵感引擎**：个人美学内核负责判断，风格与领域语言可以更换。UI 是当前主要验证场景，不是引擎最终边界。

当前交付物是独立 Rust workspace 中的 CLI 研究原型，尚未集成进星晴正式桌面应用，也没有面向真实用户的审阅 GUI。

```text
药材 work / asset
  → 手法 technique × 火焰 model
  → 按维度的药液 extract → 背包 inventory
  → 配方 recipe（槽位、配比、极性、语境、约束）
  → 丹药 pill（合成规格文本、预检分）
      ├─ 规格文字评判 → 多裁判合议 → 待人工队列 → 批量回填 → 权重校准
      └─ 简报 brief → 编码 agent 制作页面 → 截图 / 源码静态验收
                                                     └─ 尚未回流成配方质量证据
```

**结论：骨架与主要命令已落地，局部样例跑通；可信评测、完整可重放和真实个人学习尚未闭环。**

## 4. 必须更正的历史口径

### 4.1 “人工校准”目前是演示，不是真实人评

前序助手自行执行回填写入的 7 个 human_score，不是用户提交的评分。当前校准仅使用其中 run 14 的 3 对比较，得到 local ≈1.1429、gemini-lite ≈0.8571。

这些权重只能证明代码路径会更新权重，**不能证明 local 更符合用户审美**。当前数据库也没有评分者身份、来源类型等字段来排除 AI 演示数据；panel 已会读取这些演示权重。

### 4.2 BT 的 100 不是审美满分

当前实现把批次内最大相对强度归一到 100。它表示“在这批比较里最强”，不是绝对质量，更不能直接跨 run 比较。固定把 <40 当作低质量转人工，缺少与绝对质量的校准依据。

### 4.3 “每步可恢复”尚未实现

单裁判与 panel 都在外部比较全部成功后才写入 judge_run。中途限流/失败的已完成比较没有逐条检查点，不能从失败处续跑。

### 4.4 “配方 A/B”目前只比较了规格文字

已有两个配方的文本比较，但没有固定相同内容和实现条件，为两个配方分别生成页面后进行成品盲评。两个历史页面内容不同，也不能当作受控 A/B。

### 4.5 药液版本与历史复现仍有缺口

refine 缓存查询不含手法版本；refresh 会覆盖同一个 extract，而更新语句没有同步 technique_version。当前数据库中 donts、layout、部分 type 的记录版本与现行手法版本不一致。

因此不能把“保留旧药液、版本升级自动重炼、历史丹药完全可复现”列为完成。简报/验收又会按 extract_id 读取当前药液，历史结果可能受后续覆盖影响。

### 4.6 人工审阅与流水线门禁还有明确实现缺口

- panel 存储 `combined/votes/disputed`，screen 却读取单裁判格式 `win_i/reason`，因此 panel 的比较摘要会被误显示为“平”；候选列表和按标签回填仍可用。
- fill 是逐条校验后立即 UPDATE，没有整批事务；后续标签或分数错误时，前面的更新可能已经写入，不能宣称“不会写半截”。
- verify 的四项检查未通过时仍返回 `Ok(())`；验收结论需看 `passed`，不能直接把零退出码作为后续流水线放行条件。

## 6. 下一阶段顺序

### P0 · 先把现有证据变可信

1. 为评分记录增加真人 / AI / 演示来源、评分者、维度；演示记录不得进入真实偏好校准。
2. 修复药液版本与不可变快照，保证历史丹药、简报、验收可追踪。
3. 修复批量回填原子性、panel 审阅显示兼容；为关键规则添加自动化测试。
4. 补齐新炼丹表与评判数据的导入导出，避免搬家时只带走原始语料。

### P1 · 把“成品结果”接回配方

统一记录产物、截图、验收结果、成品评价及其来源；固定同一内容与生成条件，做一次两配方 → 两页面 → 盲评 → 配方质量统计的受控闭环。

### P2 · 再提高自动化与模型质量

加入逐对检查点、失败重试、运行参数及模型版本记录、真实 token/耗时成本；再做按维度校准、跨维度约束、真实交互素材和禁忌多图归纳。

### P3 · 接回 ToC 主线

让真实个人判断更新美学内核，并实际影响选药与配方，而不是只更新公共裁判权重。跨域迁移需要实证，不能仅凭两域数据在库里就宣称成立。
