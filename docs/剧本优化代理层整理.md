

这份文档将 Prompt 视为“软件模块”，以下是针对不同阶段初步进行了模块化整理：

### 1. 架构师代理：大纲提炼与世界观提取

此阶段的目标是将原本模糊的小说文本转化为结构化的、可视化的“工程蓝图”。

- **核心认知架构（Role）：** 定义 AI 为“资深概念艺术家和世界观架构师” 11。

- **世界观提取（Series Bible Extraction）：**
  
  - **视觉优先原则：** 指令必须要求 AI 忽略角色内心独白，专注于提取物理特征、环境细节和光影氛围 22。
  
  - **核心标签（Visual DNA）：** 要求生成不可变的角色视觉标签（如 `<visual_dna>银色短发, 赛博义眼</visual_dna>`），用于后续锚定绘图一致性 3333。
  
  - **冲突映射：** 要求分析核心冲突（如自然 vs 科技），并将其定义为具体的视觉隐喻 4。

- **大纲结构化（Beat Sheet Generation）：**
  
  - **双阶段精炼：** 强制先生成宏观的“故事弧光”，再细化为“场面节拍”，禁止一次性生成详细脚本 5。
  
  - **结构化输出表格：** 要求输出包含“节拍类型”（激励事件/高潮）、“情感电荷”（+/-）、“视觉重点”和“预估格数”的表格 6。

### 2. 编剧代理：剧本生成与格式化

此阶段的目标是生成符合工业标准、可直接用于分镜转化的文本。

- **核心认知架构（Role）：** 定义 AI 需遵循“Fountain 语法”和“展示而非讲述”原则。

- **格式即法律（Strict Syntax）：**
  
  - **Fountain 格式强制：** 场景标题全大写（INT./EXT.），角色名居中，严禁使用无关的 Markdown 符号 7。
  
  - **垂直流动感：** 限制动作描写（Action Blocks）长度不超过 3~4 行，强制 AI 将复杂动作拆解为独立的视觉镜头 8888。

- **内容约束（Negative Constraints）：**
  
  - **反心理描写（Anti-Psychologizing）：** 严禁描写“他感到悲伤”或“他想起童年”。必须通过 System Prompt 强制将心理活动转化为物理动作（如“他摩挲表盖”） 9。
  
  - **潜台词注入：** 要求角色通过撒谎、回避或反讽来表达意图，禁止直白的对话（On-the-nose） 10。
  
  - **呼吸原则：** 限制单个气泡文字量（如不超过 30 个汉字/25 个单词），超量需拆分 11。

### 3. 大纲与剧本优化：逻辑自检与节奏控制

此阶段利用“元认知”提示词对生成内容进行迭代优化。

- **翻页工程（Page Turn Engineering）：**
  
  - 在 System Prompt 中指示 AI 识别惊奇或揭秘时刻，并强制将其安排在偶数页的最后一格（右下角），驱动读者翻页 12。

- **动作原子化（Action Atomization）：**
  
  - 对于“他杀出重围”这类高密度文本，提示词需引导 AI 将其像慢动作回放一样拆解为关键帧序列 13。

- **元认知循环（Metacognitive Prompting）：**
  
  - **自我批判机制：** 要求模型在输出前先进行 `<scratchpad>` 思考或自我审查 14。
  
  - **具体检查点：**
    
    - “检查：动作是否符合物理定律？” 15
    
    - “检查：本页对话量是否遮挡超过 30% 画面？” 16
    
    - “检查：是否存在时代穿帮（如古代出现手机）？” 17
  
  - **自动修正：** 发现错误后自动执行修正循环，而非输出错误结果 18。

### 4. 推荐的 System Prompt 结构示例

根据文档建议，一个完整的 System Prompt 应包含以下 XML 封装的模块 19：

XML

```
<system_prompt>
    <role_definition>
        你是一位严格遵循视觉逻辑的漫剧编剧。你不知道角色的内心想法，只能看到他们的动作。
    </role_definition>

    <series_bible>
        </series_bible>

    <constraints>
        <syntax> 使用标准 Fountain 格式 </syntax>
        <negative> 严禁使用心理动词（觉得、认为） </negative>
        <dialogue> 单个气泡不超过 30 字 </dialogue>
    </constraints>

    <instruction>
        1. 阅读输入文本。
        2. <thinking> 在草稿区进行节拍拆解与视觉化分析。 </thinking>
        3. 输出最终剧本。
    </instruction>
</system_prompt>
```

将图片利用llm转为json描述，可以更好的控制一致性，比如这个提示词：
Analyse this image in exhaustive JSON detail。

这其实是将**非结构化的视觉信息（Unstructured Data）转化为结构化的配置参数（Structured Configuration）**。

与**“AI漫剧创作Prompt指导原则”**中提到的**“世界观提取”**和**“核心标签锁定”**理念完全吻合，且从工程实现角度来看，JSON 格式比纯文本描述更具鲁棒性。

结合文档内容，这种方法之所以有效，是因为它构建了一个**“数字化视觉 DNA 库”**。以下是如何将其系统化落地的分析：

### 1. 为什么 JSON 能解决一致性问题？

根据文档，AI 模型在处理长文本时容易遗忘早期设定 。而 JSON 的优势在于：

* **消除语义歧义：** 自然语言（如“帅气的衣服”）存在解释空间，而 JSON 键值对（如 `"clothing_material": "leather", "color_hex": "#000000"`）是确定的参数。
* 
**强制注意力聚焦：** 文档提到，结构化的上下文注入（如 XML/JSON）相当于为模型挂载了一个外部数据库，使其能精准回溯校验 。


* 
**解耦视觉元素：** JSON 可以将“人物本身”（Visual DNA）与“环境/光影”（Context）彻底分离，符合文档中提到的“参数拆解协议” 。

### 3. 工程化落地工作流 (Pipeline)

结合文档提到的**“一致性监理代理”** ，您可以构建如下自动流：

1. **资产数字化 (Asset Ingestion)：**
* 输入：角色立绘（如您的《天狼寨》角色“刘岐”）。
* 处理：LLM 运行 `Analyse... JSON` 提示词。
* 输出：生成 `LiuQi_Profile.json`。


2. **核心标签锁定 (Locking)：**
* 在后续脚本生成分镜提示词时，System Prompt 强制调用该 JSON 中的 `"character_core"` 字段。
* 
**Prompt 逻辑：** “在生成提示词时，必须包含以下来自 JSON 的描述：`{LiuQi_Profile.character_core}`。严禁修改。” 




3. **动态场景融合：**
* 保持 JSON 中的人物描述不变，仅动态替换 `"technical_specs"` 中的光影和角度参数（根据剧本的情绪需求调整） 。


### 4. 总结

使用 JSON 描述作为中间层，本质上是将**“Prompt Engineering”升级为“Configuration Engineering”**。它将模糊的自然语言变成了可版本控制、可校验的代码.
