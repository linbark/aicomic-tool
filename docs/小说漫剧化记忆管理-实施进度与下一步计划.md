# 小说漫剧化记忆管理：实施进度与下一步计划

> 适用场景：**逐章输入小说 → 逐章解析 → 迭代构建世界观/角色演变记忆 → 产出漫剧资产（大纲/节拍/剧本/分镜提示词）**
>
> 本文是对当前对话中“最终方案”的**工程化落地版本**：包含方案摘要、已落地模块/接口、实施进度与下一步计划。

---

## 1. 最终方案摘要（已确认的关键取舍）

### 1.1 总原则
- **Evidence-first**：所有记忆条目必须能追溯到原文证据（推断也必须挂证据集合）。
- **Canonical-first**：长期“真值”以结构化库为准；向量库只负责召回与辅助检索。
- **Time-as-constraints**：故事时间经常缺失、且倒叙/插叙多；用“时间约束图（partial order）+ 时间块（TimeBlock）”表示可解的部分序，并允许逐章回填与修订。
- **Human-in-the-loop**：矛盾/歧义/高风险变更进入人工确认队列（ChangeSet/Conflict 审阅台）。

### 1.2 记忆分层（生成时按层拼装上下文）
- **L0 Buffer/Workspace（短期工作台）**：当前回合临时上下文、推理草稿、待办（可清洗）。
- **L1 Canonical Store（结构化真值库）**：Entity/Snapshot/Event/StateChange/ChangeSet/Conflict/Evidence + 世界规则/负向约束（支持版本化与审计）。
- **L2 Vector Store（语义检索库）**：对 evidence/summary/条目摘要向量化，用元数据过滤召回；不作为最终真相。

### 1.3 角色演变与世界观演进（关键结构）
- **角色 = Core + TimelineSegments（用 Snapshot 表达）**
  - Core：尽量不可变（例如 Visual DNA Core），只有“形态变更事件”允许变更。
  - TimelineSegments：外观增量、性格/情绪态、目标、关系、伤势、道具、能力等；允许从行为/对话推断（默认 hypothesis）。
- **激进切片策略（已确认）**
  - 每章全量抽取时，允许为关键实体生成新的 Snapshot（即使只是“补充/细化”）。
  - 为避免生成上下文爆炸：生成侧不直接注入全部 snapshots，而是将 **每个实体的“最新 profile（当前设定）”覆盖写入 `STATIC_BIBLE`**，作为 L3 主要输入；历史 snapshots 仍保留在 Canonical 以便追溯/审计/回滚。
- **世界规则版本化**
  - 支持 `confirmed / hypothesis / retconned` 状态机；
  - 后文推翻前文：旧规则 retconned，并记录证据来源，不覆盖删除。

## 2. 当前代码落地位置（后端）

> 说明：本轮落地优先复用项目现有“记忆系统”结构：`MemoryStore (SQLite+Vector)` + `MemoryRetriever` + `AI Router` 注入上下文。

### 2.1 Canonical 最小合同（Schema Contract）
- 位置：`backend/app/workflows/memory_schemas.py`
- 已新增/扩展：
  - `MemoryNamespace.CANONICAL`
  - `MemoryType` 扩展：`EVIDENCE/ENTITY/SNAPSHOT/STATE_CHANGE/CHANGESET/CONFLICT/TIME_CONSTRAINT/TIME_BLOCK`
  - 真值与来源：`TruthStatus / SourceKind`
  - 故事时间：`StoryTime`
  - 时间约束：`TimeConstraint`（before/after/during/overlaps/flashback_of/within_interval/anchored_to）
  - 时间块：`TimeBlock`
  - `MemoryRecord` 扩展字段：`status/confidence/source_kind/evidence_ids/story_order/story_time`
  - `MemoryQuery` 扩展过滤字段：`status/min_confidence/source_kind`
  - Canonical payload 最小模型：
    - `EvidenceRecordPayload`：新增 `project_id`（Evidence-first）
    - `CanonicalEntityPayload`：实体主干最小合同
    - `CanonicalSnapshotPayload`：切片最小合同（自由 fields，顶层命名空间建议固定）

### 2.2 Canonical Store（SQLite 表结构 + 读写）
- 位置：`backend/app/services/memory_store.py`
- 关键实现：
  - `memory_records` 表：增加 canonical 扩展列（并做了轻量迁移 + 显式列读取，避免 SELECT * 下标错位）。
  - 新建 canonical 表（用于结构化真值与审阅台最小闭环）：
    - `canonical_time_constraints` / `canonical_time_blocks`
    - `canonical_changesets` / `canonical_conflicts`
    - 以及为后续扩展预留的骨架表：`canonical_entities/canonical_events/canonical_snapshots/canonical_state_changes/canonical_evidences`
  - 时间约束/时间块 API 内部实现：
    - `upsert_time_constraint / list_time_constraints`
    - `upsert_time_block / list_time_blocks`
  - 审阅台（ChangeSet/Conflict）最小实现：
    - `create_changeset / list_changesets / get_changeset`
    - `apply_changeset / reject_changeset`
      - `apply_changeset` 现支持应用 payload 中的：
        - `evidences` → `canonical_evidences`
        - `entities` → `canonical_entities`
        - `snapshots` → `canonical_snapshots`
        - `time_constraints/time_blocks`
      - 并支持 **materialize（兼容生成链路）**：把每个实体的“最新 confirmed snapshot”覆盖写入 `STATIC_BIBLE`（每实体一个固定 profile id）
    - `create_conflict / list_conflicts / resolve_conflict`

### 2.3 Vector Store 元数据扩展与降级机制
- 位置：`backend/app/services/vector_store.py`
- 关键实现：
  - 向量 payload 增加 canonical 元数据：`status/confidence/source_kind/evidence_ids/story_order/story_time`
  - 支持 `MemoryQuery.status/min_confidence/source_kind` 过滤
  - `qdrant_client` 缺失时可降级为进程内 fallback（避免导入即崩溃，便于不同运行环境启动）

### 2.4 生成时上下文拼装（可解释/可审计）
- 位置：`backend/app/services/context_assembly.py`
- 输出分段：
  - `L3` 世界观/角色设定（静态真值）
  - `L2` 事件链/剧情进展
  - `L1` Buffer（可选，支持注入最近消息）
  - `约束条件`（负向约束）
  - `audit_record_ids`（本次拼装使用的 record_id 列表，用于追溯）
- 接入点：
  - `backend/app/routers/ai.py` 的 `_build_memory_context()` 已改为使用该拼装模块
  - `backend/app/services/memory_retriever.py` 对 L3 与负向约束默认过滤 `status=confirmed`

### 2.5 对外接口（后端）
- 入口：`backend/app/routers/memory.py`（已在 `backend/app/main.py` 注册）
- 接口清单：
  - **时间约束/时间块**
    - `POST /memory/time-constraint`
    - `GET /memory/time-constraints`
    - `POST /memory/time-block`
    - `GET /memory/time-blocks`
  - **审阅台：ChangeSet**
    - `POST /memory/changeset`
    - `GET /memory/changesets`
    - `GET /memory/changeset/{changeset_id}`
    - `POST /memory/changeset/{changeset_id}/approve`
    - `POST /memory/changeset/{changeset_id}/reject`
  - **审阅台：Conflict**
    - `POST /memory/conflict`
    - `GET /memory/conflicts`
    - `POST /memory/conflict/{conflict_id}/resolve`

## 4. 下一步计划（建议按优先级推进）

### P0（让整条链路跑起来：逐章输入 → 变更集 → 审阅 → 产出）
1. **Chapter/Evidence 入库接口（Evidence-first）**
   - 将章节原文切片为 Evidence（quote + span + tags + speaker），写入 `canonical_evidences`
   - 已新增 API：`POST /memory/evidence/ingest`
     - 切片策略（v0）：按空行分段（paragraph），段落过长按字符长度继续切分
     - 产物：返回 `evidence_ids[]`，并同步写入 `CANONICAL` namespace 的 `MemoryRecord(type=EVIDENCE)` 便于语义检索/审计
2. **抽取器输出统一为 ChangeSet payload**
   - 抽取：实体/事件/状态变更/推断（默认 hypothesis）+ 时间约束
   - 产出：`ChangeSet.payload_json`（含 proposed_* 与 conflicts）
3. **审阅台 UI（最小版）**
   - 能看 ChangeSet / Conflict

4. **定稿 ChangeSet payload v0（用于可执行提交）**

5. **ChangeSet payload 统一入口（便于抽取器/前端上送）**
   - 已新增 API：`POST /memory/changeset/from-payload`
   - 行为：
     - 默认补齐 `schema_version=changeset.v0`

     - 默认 `materialize.write_static_bible=true`（保证激进切片不会炸生成上下文）

### P0 最小闭环调用顺序（建议你先用 Postman/前端按钮串起来）
1. `POST /memory/evidence/ingest`（传 project_id + episode_id + 章节原文 text）
2. 抽取器（暂可人工/外部）生成 `changeset.v0` payload（引用上一步返回的 evidence_ids）
3. `POST /memory/changeset/from-payload` 创建变更单
4. `POST /memory/changeset/{id}/approve` 批准提交（会落 canonical_* + materialize 写回 STATIC_BIBLE）
5. 调用生成接口（如 `/ai/generate-script`），确认 L3 可检索到 `profile::<entity_id>` 的“当前设定”

## 5. 备注：本方案与现有系统的衔接方式
- 现有系统已有：SeriesBible/VisualDNA（file-first）→ MemoryIndexer（原子化向量索引）→ MemoryRetriever（分层检索）→ AI Router 注入。
- 本轮新增的是：**Canonical 真值库与审阅闭环**，用于支撑“逐章迭代构建 + 可回滚/可审计 + 倒叙插叙时间线”。
